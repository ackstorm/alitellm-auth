## 0. Summary

1. **Every OpenCode client (CLI and the OpenWork desktop on engine v1) gets its
   configuration from its backend, per user, through the existing auth plugin.**
   The plugin already works against both platform and ACH (it discovers the
   authorization server by RFC 9728/8414 from one URL). Its `config` hook calls
   `GET /api/opencode/config` on the backend and merges the response *under* the
   user's own config (user always wins), like OpenCode's remote-config layer.
   The response schema `ackstorm.opencode-config/1` (§4.2.1) is the shared
   contract: platform and ACH each implement it. This replaces
   `OPENCODE_MODELS_URL`, manual provider setup and manual MCP setup.
2. **No new user steps.** Users keep doing exactly what they do today:
   `opencode plugin https://<backend>/public/opencode-auth -g` then
   `opencode auth login -p ackstorm`. Config is rebuilt on every start.
3. **No new long-lived credential.** The hook uses the OAuth token the plugin
   already holds and refreshes.
4. **OpenWork Den shrinks to what only it can do**: desktop sign-in, **enforced**
   desktop policy (the plugin only sets overridable defaults), branding, and
   onboarding (install link, MDM bootstrap). It serves no models and no skills:
   a skill needs an authenticated model to run, and before the plugin is signed
   in there is none. **Den stays inside alitellm-auth** (`app/openwork.py`);
   it is not extracted into a separate service (D-12).
5. Platform and ACH remain **separate products**.

## 1. Goals and non-goals

### Goals
- G-1 A user's model list, model capabilities (image input, context, cost), MCP
  servers and skills are defined server-side, per user, and reach both the
  OpenCode CLI and OpenWork without editing files or setting env vars.
- G-2 Nothing sensitive is served unauthenticated. No static token is written to
  disk beyond what OAuth already stores.
- G-3 Platform being down must not stop OpenCode from starting.
- G-4 User config (global `~/.config/opencode/opencode.json`, project
  `opencode.json`) always overrides what platform delivers.

### Non-goals
- Enforcement. Platform delivers defaults; it does not lock anything. Hard
  enforcement is MDM / OpenCode managed config, out of scope.
- Hot reload inside a running session. Config applies at the next start.
- OpenWork engine v2 (`opencode2`). Not supported by this design; see §6.3.
- Pushing OpenCode plugins from the server. The auth plugin is installed by
  the user with two terminal commands (§4.4 onboarding order).

## 4. Design: per-user client config

### 4.1 Flow

```
opencode / OpenWork engine v1 start
  └─ load config (global, OPENCODE_CONFIG, project, .opencode)          [cfg]
  └─ load plugins (auth plugin from global config)
       └─ plugin.config(cfg)                                            [awaited]
            ├─ bootstrap: platform base URLs (§4.3.1)
            ├─ access token: stored OAuth for "ackstorm", refresh if needed
            ├─ GET {platform}/api/opencode/config  (Bearer, 2 s timeout)
            │     ok  → write cache, use body
            │     err → use cache if same user and < 30 d, else nothing
            ├─ fillMissing(cfg, body.config)        user keys always win
            └─ materialize body.skills → cfg.skills.paths += dir
  └─ provider / agent / mcp / skill services read cfg
```

Verified: OpenCode awaits every plugin's `config` hook and logs-and-ignores a
throw (`packages/opencode/src/plugin/index.ts:245-252`); providers are read after
plugins "so config() hook runs before reading cfg.provider"
(`provider/provider.ts:1440-1444`); agents depend on the plugin service
(`agent/agent.ts:93`). **Not verified**: that `mcp` and `skills` state is built
after the hook for every entry point (`mcp/index.ts:496`, `skill/index.ts:211`
read the same `cfg` object). Test T-P6 is mandatory before relying on it.

### 4.2 Server: `GET /api/opencode/config`

**Route**: `app/opencode_config.py` (new router), registered in `create_app()`
before the `/public` mount. Host: platform (same app as `/api/*`).

**Auth**: `Authorization: Bearer <front-door access token>` as issued by this
app's AS (`app/oauth_as`). The app does not verify these JWTs today (the Go
authz does, on `api.*`). Add `Signer.verify(token) -> claims` in
`app/oauth_as/tokens.py` using the same key pair: check signature, `iss ==
settings.as_issuer`, `aud == settings.as_audience`, `exp`. Identity = `sub`
(the user's email, same as `resolve_front_key(sub)`). No session cookie, no
same-origin guard (non-browser GET), `Cache-Control: no-store`.

**Status codes — hard rule**: this endpoint returns **200 JSON** for any request
that carries a syntactically valid Bearer, even when the token is expired,
revoked or the user is unknown. In that case the body is the *baseline*
(§4.2.3) plus `"auth": "invalid"`. Rationale: the plugin must be able to tell
"sign in again" from "platform down", and nothing in the client path should
depend on status parsing. Missing/malformed header → 401 (the plugin never
sends that).

#### 4.2.1 Response schema

```json
{
  "schema": "ackstorm.opencode-config/1",
  "version": "sha256:<hex of canonical JSON of config+skills>",
  "user": "jane@example.com",
  "environment": null,
  "auth": "ok",
  "stale": false,
  "generatedAt": "2026-09-27T10:00:00Z",
  "config": {
    "provider": {
      "ackstorm": {
        "name": "ACKstorm",
        "npm": "@ai-sdk/openai-compatible",
        "options": { "baseURL": "https://api.ackstorm.ai/v1" },
        "models": {
          "ackstorm.smart": {
            "name": "ACKstorm Smart",
            "attachment": true,
            "tool_call": true,
            "modalities": { "input": ["text", "image"], "output": ["text"] },
            "limit": { "context": 200000, "output": 32000 },
            "cost": { "input": 3, "output": 15 }
          }
        }
      }
    },
    "mcp": {
      "mcp-aws-eks-ro": {
        "type": "remote",
        "url": "https://api.ackstorm.ai/mcp/mcp-aws-eks-ro",
        "enabled": false
      }
    }
  },
  "skills": [
    { "name": "mcp-setup", "version": "sha256:<hex>", "files": { "SKILL.md": "---\nname: mcp-setup\n..." } }
  ]
}
```

- This schema is shared with ACH (`takeover-ach.md` §3) and must stay identical. `environment` is always `null` on platform (no environments); ACH sets it.
- `config` is OpenCode config (v1 schema). Allowed top-level keys in v1 of this
  endpoint: `provider`, `mcp`, `instructions`. Anything else is a server bug;
  the plugin ignores unknown keys (§4.3.3).
- `config` **never** contains: `plugin`, `permission`, `agent`, `command`,
  `enabled_providers`, `disabled_providers`, keys or tokens, `{env:…}` or
  `{file:…}` templates. Platform must not be able to install code or widen
  permissions on clients.
- `skills[].files` is inline text; only `SKILL.md` in v1; max 256 KiB per file,
  max 50 skills. `name` is kebab-case ≤ 64.

#### 4.2.2 Building the config (per request, cached per user)

1. **Models.** Load `/app/public/opencode/api.json` (operator output; reload on
   mtime change). Take the provider entry whose id is `ackstorm` (constant
   `OPENCODE_PROVIDER_ID`, must equal the plugin's `PROVIDER`). Fetch the
   user's visible model groups with `list_litellm_models(settings,
   await _user_key(email, settings))` (same call as `GET /api/session/models`).
   Output models = `api.json` models whose id is in the user's list. Copy per
   model only these keys: `name, family, release_date, attachment, reasoning,
   temperature, tool_call, interleaved, cost, limit, modalities, status,
   options, headers, variants`. Provider block: `name`, `npm`, `api`, `options`
   from `api.json`; **drop `env`** (auth comes from the plugin; an `env` entry
   would re-enable the `LITELLM_API_KEY` override).
2. **MCP servers.** For each key in `settings.services` (`AS_SERVICES`) the user
   may use: `{type: "remote", url: "{API_PUBLIC_URL}/mcp/{svc}", enabled: false}`.
   "May use" = present in `list_litellm_mcp_servers` under the user key (the
   helper behind `GET /api/session/mcp`). **Caveats**: (a) the mapping from an
   `AS_SERVICES` key to a LiteLLM MCP server name is not settled (§8 Q-3);
   (b) CLAUDE.md "Known gap — MCP": a team's `mcp_servers: []` does not deny,
   so LiteLLM's per-user MCP list can be proxy-wide. Until both are settled,
   include every `AS_SERVICES` key; a user without access fails at LiteLLM
   (403 entitlement) after sign-in, which the skill explains.
3. **Skills.** v1: `mcp-setup` only, rendered by `app.skills.mcp_setup_body(settings)`
   (Appendix B.2, task T1).
4. **Instructions.** None in the normal case. Baseline with `auth: "invalid"`
   adds nothing to `config`; the plugin surfaces the message (§4.3.4).
5. **Degradation.** Keep the last good result per user in Redis
   (`opencode_config:{email}`, TTL 30 d; reuse the `oauth_as` store). If
   LiteLLM fails, return that entry (`"stale": true`). If there is none, return
   the baseline: `api.json` provider with **all** its models, no MCP, skills.
   Never 5xx for upstream failures.
6. **Baseline** (unknown/invalid token): `{schema, version, user: null,
   environment: null, auth: "invalid", config: {}, skills: []}`. Do not leak the org's model or MCP list
   to an unauthenticated caller.

#### 4.2.3 Server limits
- p95 < 300 ms warm; hard deadline 1.5 s, after which serve the cached entry.
- Response < 1 MiB.
- Log `user`, `version`, `stale`; never log tokens or skill bodies.

### 4.3 Plugin changes — `clients/opencode/index.mjs`

#### 4.3.1 Platform bootstrap (remove the dependency on api.json)
The hook runs before the `ackstorm` provider exists (it is what creates it), so
discovery cannot read the provider from config any more.

- `GET /public/opencode-auth` serves the tarball with an extra file
  `platform.json`: `{"api": "<API_PUBLIC_URL>", "platform": "<APP_BASE_URL>"}`.
  Generate it at app startup by repacking the baked tgz (deterministic mtime so
  the tarball bytes are stable per deployment). Each deployment's plugin thus
  knows its own endpoints.
- Override: plugin options. OpenCode passes the second element of a tuple spec
  to the plugin (`plugin/index.ts:118`, `server(input, load.options)`):
  `"plugin": [["https://…/public/opencode-auth", {"api": "…", "platform": "…"}]]`.
- `discover()` uses `platform.json.api` (or the option) as the API URL, then
  RFC 9728 → RFC 8414 as today. Remove `client.config.providers()` from it.

#### 4.3.2 Token in the hook
- Read the stored credential for `ackstorm` from
  `$XDG_DATA_HOME/opencode/auth.json` (the hook has no `getAuth`). If absent or
  not `type: "oauth"` → skip the fetch, use nothing (not the cache: the user
  signed out).
- If `expires < now + 60 s`: refresh with the same code path as `loader.fetch`
  (share one function and the `refreshing` guard). Persist with
  `client.auth.set`. If that call fails because the server is not up yet,
  keep the new tokens in a module variable that `loader.fetch` reads first.
  **Must not** write `auth.json` directly (two writers).
- A failed refresh (`invalid_grant`) = signed out: no fetch, show the
  sign-in message (§4.3.4).

#### 4.3.3 Merge rule `fillMissing(target, source)`
- Only keys in the allow-list (`provider`, `mcp`, `instructions`) are read from
  `source`; everything else is ignored.
- Objects: recurse. A key absent in `target` is copied from `source`.
- Scalars and arrays present in `target`: keep `target`.
- `instructions`: append the source entries not already present.
- Consequences: a user's `mcp.x.enabled: true` sticks; a user-defined model
  under `provider.ackstorm.models` keeps its values and gains missing ones;
  deleting a server/model on the platform removes it at the next start unless
  the user defined it themselves.

#### 4.3.4 Cache and failure handling
- File `$XDG_DATA_HOME/opencode/ackstorm-config.json`, mode 0600:
  `{user, version, fetchedAt, body}`.
- Fetch with `AbortSignal.timeout(2000)`. On success with `auth: "ok"`: write
  cache, use body. On `auth: "invalid"`: delete cache, use nothing, set a
  one-line notice. On network error/timeout/non-200: use cache if
  `cache.user` equals the token's `sub` and `fetchedAt` < 30 d.
- The hook never throws. Wrap everything; log once.
- Notice: add to `cfg.instructions` a single inline string such as
  "ACKstorm sign-in expired: tell the user to run `opencode auth login -p
  ackstorm`". **Verify** OpenCode accepts inline text in `instructions` (it is
  documented for paths/URLs/globs). If not, drop the notice; do not create files.

#### 4.3.5 Skills materialization
- Directory `$XDG_DATA_HOME/opencode/ackstorm-skills/<name>/SKILL.md`, 0600/0700.
- Write only when `version` differs from `<name>/.version`; delete directories
  of skills no longer listed.
- Append the directory to `cfg.skills.paths` (create the array if missing).

#### 4.3.6 Release
- Bump plugin version; users re-run `opencode plugin <url> -g -f` once (the
  tarball is fetched at install and on first launch only; TODO.md).

### 4.4 OpenWork (engine v1)

### 5.4 Connect direct MCP exposure (deferred, D-9)
Resource `openwork://connect/mcp-servers/index.json`, schema

## 6. Constraints and risks

- 6.1 **Unverified hook ordering for `mcp`/`skills`** (§4.1). Mitigation: T-P6
  before rollout.
- 6.2 **Startup latency**: up to 2 s added when platform is slow. Cache makes
  the common case a local read after the first fetch is abandoned. Consider
  "use cache immediately, refresh in background for next start" if pilots
  complain. Not in v1 (YAGNI).
- 6.3 **OpenWork engine v2** runs `opencode2` with its own
  `OPENCODE_CONFIG_DIR` and a different config loader. It is unknown whether it
  loads the user's global plugins. If it does not, neither the OAuth model
  path nor this hook works there, and OpenWork v2 would need models via Den
  (`llmProviders` with a fixed `lpr_` id) and auth via Den. Re-evaluate when
  OpenWork makes v2 the default.
- 6.4 **Config is a defaults layer, not policy.** Users can override or remove
  anything locally.
- 6.5 **Plugin trust**: the plugin runs with user privileges; the server must
  never be able to change what code runs (hence no `plugin` key, §4.2.1).
- 6.6 **Operator coupling**: model capabilities come only from `api.json`
  (alitellm-operator). A model visible in LiteLLM but absent from `api.json`
  is not delivered. Intended: the operator is the source of truth for
  capabilities.

### B.1 `src/api/app/skills/mcp-setup.md`

~~~~markdown
---
name: mcp-setup
description: Add this organization's MCP servers to OpenCode (globally or for one project) and sign in to them with OAuth. Use when the user wants to connect, add, enable, authenticate, re-authenticate, troubleshoot or remove an MCP server.
---

# MCP setup

Every MCP server below is reached through the organization's gateway and signs in with
OAuth. No API key, `sk-` key or bearer token ever goes into a config file: OpenCode runs
the sign-in itself the first time the server answers 401, and keeps the tokens in its
own store.

## Available servers

{{servers}}

If the server the user wants is not listed, it is not available through this gateway.
Say so and stop; do not invent a URL.

## 1. Choose the scope

Ask the user which one they want, unless they already said:

- **Global** (every project): `~/.config/opencode/opencode.json`, or `opencode.jsonc`
  if that is the file that exists.
- **This project only**: `opencode.json` (or `opencode.jsonc`) at the project root.
  It is usually committed, and that is fine: the entry holds only a URL.

## 2. Add the entry

Read the file first. Merge into the existing `mcp` object; never rewrite the file or
drop keys you did not add. Keep comments in a `.jsonc` file. If the file does not exist,
create it with `"$schema": "https://opencode.ai/config.json"`.

```json
{
  "mcp": {
    "<name>": {
      "type": "remote",
      "url": "<url from the list above>",
      "enabled": true
    }
  }
}
```

Use the server name from the list as `<name>`. Do not add `headers` or an `oauth` block:
the defaults are what make the OAuth sign-in work, and `"oauth": false` disables it.

## 3. Sign in

OpenCode and OpenWork only read the config at startup, so tell the user to restart
OpenCode (or OpenWork) after editing it. Then either:

- **In a terminal:** `opencode mcp auth <name>` opens the browser. Run it for the user
  if you have a shell and they are at this machine.
- **In the chat:** the first time a tool of that server is used, OpenCode shows a sign-in
  link. Tell the user to open it.

The sign-in can show two screens: the organization's single sign-on, then, for servers
that act on an external account, that provider's consent screen. Both are expected.

## 4. Check

`opencode mcp list` shows every server and whether it is signed in. For one server
that does not connect, `opencode mcp debug <name>` explains why.

## Troubleshooting

- **401 after signing in:** the session expired or was revoked. Run
  `opencode mcp logout <name>`, then `opencode mcp auth <name>`.
- **403 `insufficient_scope`:** the sign-in did not grant this server. Sign in again as
  above; if it persists, the user's account lacks access to that server and an
  administrator must grant it.
- **Server missing from `opencode mcp list`:** wrong file, invalid JSON, or OpenCode was
  not restarted.

## Removing a server

Delete its entry from the config file and run `opencode mcp logout <name>`.

## Rules

- Never read, print or copy `~/.local/share/opencode/mcp-auth.json`; it holds tokens.
- Never put a key or token in a config file, an environment variable or the chat.
- Change only the `mcp` entries the user asked for.
~~~~

### B.2 `src/api/app/skills/__init__.py`

~~~~python
# SPDX-License-Identifier: Apache-2.0
"""Skills served to OpenCode clients.

Each skill is a SKILL.md template next to this module. Templates are rendered
per request from Settings; nothing here reads user data. Delivered by
`GET /api/opencode/config` (docs/superpowers/specs/2026-09-27-opencode-client-config-and-den.md
§4.2.2), not by the OpenWork Den.
"""

from __future__ import annotations

from pathlib import Path

from app.config import Settings

MCP_SETUP = "mcp-setup"
_TEMPLATE = (Path(__file__).parent / f"{MCP_SETUP}.md").read_text()


def mcp_setup_body(settings: Settings) -> str:
    """SKILL.md for mcp-setup with the gateway's OAuth MCP servers filled in.

    The list is AS_SERVICES: exactly the services a front-door token can carry as
    a scope, so every entry is one OpenCode can sign in to. No per-user filtering
    here; a server the user may not use answers 403 insufficient_scope, which the
    skill explains.
    """
    base = settings.api_public_url.rstrip("/")
    names = sorted(settings.services)
    if names and base:
        servers = "\n".join(f"- `{name}`: `{base}/mcp/{name}`" for name in names)
    else:
        servers = "None are configured on this gateway yet."
    return _TEMPLATE.replace("{{servers}}", servers)
~~~~

~~~~python
def test_mcp_setup_lists_the_oauth_services_sorted():
    services = (
        '{"mcp-google-drive": {"store": "google-drive", "broker": "https://b.test/g"},'
        ' "mcp-aws-eks-ro": {"store": "aws-eks-ro", "broker": "https://b.test/a"}}'
    )
    text = mcp_setup_body(
        _settings(as_services=services, api_public_url="https://api.example.com/")
    )
    assert text.startswith("---\nname: mcp-setup\n")
    assert "{{servers}}" not in text
    assert (
        "- `mcp-aws-eks-ro`: `https://api.example.com/mcp/mcp-aws-eks-ro`\n"
        "- `mcp-google-drive`: `https://api.example.com/mcp/mcp-google-drive`"
    ) in text

    text = mcp_setup_body(_settings(as_services="", api_public_url="https://api.example.com"))
~~~~
