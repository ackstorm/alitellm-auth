01Verdict

All three authentication paths work and none of them can be subverted. The identity boundary is sound: I could not impersonate another user, forge a token, replay a code, or reach an internal endpoint from the edge.

The defects are not in who the platform thinks you are — that is correct on every path — but in what that identity is then allowed to reach. Signing in with OAuth lands you on a virtual key scoped to a different LiteLLM team than the key you create in the console, and that team carries a far smaller model catalog. In practical terms: every OAuth-authenticated client gets 72 models with zero Claude and zero Bedrock, while the same human's console key gets 392 including all of them.

Secondary: the MCP gateway rejects OAuth tokens outright on the deployed build (fixed in the repo, not yet shipped), and disabling a key in the console takes up to a minute to actually bite.

State integrity verified

Two throwaway keys were created and deleted during the lifecycle phase. The final key inventory is byte-identical to the pre-test snapshot: same 10 keys, same aliases, same default key (default, team dream). Nothing in the cluster was mutated — no Helm, no kubectl apply, no restarts. Approximately 5 chat completions were billed against the account.

04Findings

F1 — OAuth sign-in yields a key with no Claude and no Bedrock high

The OAuth front door mints a dedicated per-user key (metadata.key_alias = "front") placed in the team named by LITELLM_DEFAULT_TEAM, which in this deployment is default. Every key created through the console instead lands in a team the user actually works in — here dream. The two teams expose very different model access groups.

CredentialTeamModelsclaude.*bedrock.*
Console key (laptop)dream3891418
Console key (freshly created)dream3921418
Same key moved to runrun368——
OAuth device tokendefault7200
OAuth auth-code + PKCE tokendefault7200
Console catalog (/api/session/models)impersonated3931418

Team default carries only the access groups ['default','openai','gemini','kubeai']. The resulting catalog is Gemini, KubeAI, transcription and embeddings — no Anthropic, no Bedrock:

ackstorm.*  (11)   gemini.* (38)   kubeai.* (11)   openai.* (7, transcribe/tts/embeddings only)
claude.*     0     bedrock.*  0

Impact. Every consumer of the front door — the OpenCode plugin, ackstorm-token login for Claude Code and Codex, the device grant for headless hosts — is the exact audience most likely to want Claude, and is the only audience that cannot reach it. A user who works fine with their pasted sk- key will find the same models missing the moment they switch to SSO, with no error explaining why.

Root cause. src/api/app/internal.py mints the front key through generate_litellm_key(sub, settings, alias="front"), which uses settings.team_id — the single deployment-wide default team. There is no notion of "the team this user actually belongs to". The user here is a member of default, run and dream; the front door always picks the first.

Note. The front key is visible in the console and is marked managed: true, so moving it to dream from the UI would incidentally fix this for one user — which also means a user can silently change their own SSO capabilities, or delete the key entirely. Deletion self-heals (the resolver re-mints on rejection); a team move does not.

F2 — OAuth tokens are rejected by the MCP gateway high fix not deployed

On the deployed build, a valid user token is refused on any named MCP server while a raw virtual key succeeds on the identical request.

POST /mcp/mcp-slack   Authorization: Bearer <valid AS token>
→ 403 {"error":"insufficient_scope","scope":"mcp-slack"}
   www-authenticate: Bearer error="insufficient_scope", scope="mcp-slack",
                     resource_metadata=".../.well-known/oauth-protected-resource/mcp/mcp-slack"

POST /mcp/mcp-slack   x-genai-api-key: sk-…
→ 200  tools/list → 29 tools

This is precisely the bug described by commit 79f5c48 and released as v0.14.1, which is in the repository but not in the cluster — both deployments still run v0.14.0.

Worth noting independently of the fix: the RFC 9728 document for that resource advertises scopes_supported: ["alitellm"] only. A spec-compliant client reading the challenge could never request the mcp-slack scope the gate demanded, so the gate was unsatisfiable by construction, not merely misconfigured.

F3 — Disabling a key leaves it live for up to ~60 seconds medium

Blocking a key via the console returns 200 and LiteLLM records blocked: true immediately, but the gateway keeps accepting the key until LiteLLM's auth cache expires.

tActionResult
0sPOST /api/session/keys/{id}/block200 {"status":"blocked"}
~2sGET /v1/models with the blocked key200 full catalog returned
~3sPOST /v1/chat/completions200 completion served
~4sGET /api/oauth/whoami200
+65sGET /v1/models401 Key is blocked.

Deletion behaves the same way. The window is bounded and small, but "disable this key" is the action a person takes the moment they believe a key leaked, and during that minute the key still spends budget. The UI gives no indication that the change is not yet in force.

F4 — Duplicate key names are accepted; the collision guard is unreachable medium

Creating a second key with an alias already in use returns 200 and a second key, rather than the documented 422. LiteLLM's own uniqueness constraint applies to the opaque lk-{hex} alias, which is regenerated per key; the human-facing name lives in metadata.key_alias where nothing checks it.

This is not theoretical — it produced a genuinely ambiguous state during this audit. After blocking one of two identically-named keys, the administrative view was:

name= e2e-audit-1790022304432   blocked= None   team= dream
name= e2e-audit-1790022304432   blocked= True   team= dream

Two rows, same displayed name, opposite security state, distinguishable only by an id the console truncates. For a fleet of agent keys this is an operational hazard: revoking "the n8n key" gives no confidence you revoked the right one.

F7 — The /gemini/ prefix is protected but unusable low

Declared a protected prefix in authz, yet it returns 401 for every credential type — OAuth token and raw virtual key alike, with byte-identical errors:

{"error":{"message":"LiteLLM Virtual Key expected. Received=****, expected to start with 'sk-'.", …}}

authz rewrites the credential into x-litellm-api-key, which LiteLLM's Gemini passthrough does not read. Either the route is dead and the prefix should be dropped, or the passthrough needs the credential in the header it actually consumes. Not a security issue — a path that protects nothing because nothing reaches it.

F8 — LiteLLM's admin UI shell is served to the internet low

GET https://api.ackstorm.ai/ui/ returns 200 and the admin SPA shell with no credential. It falls outside every protected prefix, so authz never sees it and LiteLLM serves the static bundle before its own auth applies.

Authentication still gates the data behind it — /key/list, /model/info and friends all answer 401 unauthenticated, which I verified. This is attack surface and version disclosure, not an exposure. Worth an allow-list on the gateway if the admin UI is not meant to be publicly discoverable.

F9 — Dex forces full Google re-consent on every authorization informational

Three separate authorizations within roughly four minutes each presented the account chooser and the "You're signing back in to ackstorm.ai" consent screen. The Dex Google connector is sending prompt=consent:

accounts.google.com/v3/signin/accountchooser?… &prompt=consent& …

Two full clicks per login, every login, including device-code approvals from a phone. Setting promptType: "" on the connector removes it. Cosmetic, but it is the first thing every user of the front door experiences.

09What held up

Worth recording explicitly, because these are the properties that would have mattered most had they failed:

  • No impersonation is possible. x-user-id is stripped in two independent places. A valid key plus a forged user header returns the attacker's own data, not the victim's.
  • No token forgery is possible. Swapping sub, swapping aud, or replacing the signature all yield the same opaque 401.
  • PKCE is mandatory and genuinely enforced — plain refused, omission refused, implicit flow refused, wrong verifier refused and the code burned.
  • Every single-use artifact is genuinely single-use — authorization codes, device codes, refresh tokens. All replays were rejected.
  • The privilege boundary between user and master key is intact — a user key on /api/users is 403, not 200.
  • Internal endpoints are unreachable from the internet on both hostnames, blocked at the Gateway before the application sees them.
  • No secret material leaks through the console API. The key listing contains no sk- anywhere.
  • Object-level authorization is correct — foreign keys, the default key, and fabricated ids all fail closed, and the fabricated-id case returns 403 rather than 404, so it cannot be used to enumerate.
  • ext_authz is failOpen: false — an authz outage denies traffic rather than admitting it unauthenticated.
